# MultiCC 后端渐进迁移 Rust 调研

调研日期：2026-10-21。代码基线：`43266cbd`，项目版本：`2.8.3`。范围按用户最新要求收敛为 MultiCC 自有后端；网页、Flutter 客户端和桌面界面继续沿用。本报告是技术可行性与实施路线调研，本轮尚未实现 Rust 原型或测量 Rust 性能。

**结论：具备渐进迁移条件，建议以 Rust 最终接管后端为目标。** 可以先让 Node.js 保持现有入口，通过进程间接口把职责逐块交给 Rust；随后 Rust 接管 HTTP、WebSocket、任务执行与持久化，Node.js 缩减为暂存的供应商适配桥；最后逐一消除 MultiCC 对这些桥的依赖。前端无需随此项目重写。

迁移的主要价值是明确状态所有权、控制资源与并发、降低主服务受到重计算干扰的程度，以及逐步形成独立后端可执行程序。是否降低 CPU、内存、请求延迟，必须通过同负载对照验证。语言变化本身不会消除任务重复投递、状态判断错误或跨进程恢复问题。

仓库已跟踪文件中没有 `.rs` 或 `Cargo.toml`。主要运行依赖是 Node.js ≥22.16、Express、ws、Node 内置 SQLite，以及若干厂商 SDK。统计未把未跟踪依赖、外部 CLI 实现和前端代码纳入后端合计。后续实施还要盘点 `scripts/`、安装脚本和发布工作流中的后端运行依赖。

当前有利于迁移的基础：

1. [会话端口定义](../src/session/ports.js)和[架构守卫](../tests/test-architecture-boundaries.js)已经建立了一部分模块边界。已有模块可作为替换单位，但接口仍是 JavaScript 进程内接口。
2. [API 契约目录](../contracts/v1/openapi.json)有 12 个 OpenAPI 路径，另有 23 个 JSON Schema 和固定样例，可复用为跨语言验收输入。它们没有覆盖全部既有 HTTP 与 WebSocket 行为，必须逐域补齐。
3. [编排组合层](../src/orchestration/runtime.js)已经能选择存储实现；生产入口明确传入 SQLite 路径。说明渐进换实现的机制在项目内已有先例。
4. [历史消息适配器](../src/session/adapters/chat-history-file-repository.js)负责 JSONL 持久化，并兼容旧 JSON 数组；[搜索索引](../src/search/index-store.js)明确只保存可重建的派生数据。

也存在需要先处理的边界：

- `src/chat/turn-engine.js` 约 2,999 行，有 43 处静态 `require`；它联系适配器、持久化、供应商选择和回合生命周期，不宜作为第一批直接翻译。
- [SQLite 编排存储](../src/orchestration/sqlite-store.js)的 `mutate(mutator)`、`mutateIf(predicate, mutator)`、`read(selector)`接收 JavaScript 函数。函数、闭包和对象引用不能原样跨进程发送。应先收敛成 `enqueue`、`claim`、`ack`、`recordVerdict` 等明确命令，再移交对应业务事务。
- [任务壳存储](../src/task-shell/store.js)、聊天 JSONL、编排 SQLite 分属不同状态域。Rust 和 Node.js 不能各持一份可写缓存、同时自认为是同一状态的权威。
- 部分旧文档仍描述“无数据库”或每回合单次进程；实际已有 SQLite、常驻聊天进程和 SDK 路径。本报告以源码为准。

**建议的目标形态与过渡形态**

| 阶段 | 外部请求入口 | 业务与数据所有者 | Node.js 的角色 |
| --- | --- | --- | --- |
| 初期 | 现有 Node.js HTTP / WebSocket | Node.js 拥有权威状态；Rust 先负责独立派生数据 | 主服务，调用 Rust 子进程 |
| 中期 | Node.js 入口逐域转发，之后切换到 Rust | 每个迁移域只有一个权威所有者；Rust 承接完整事务 | 尚未迁移业务与厂商桥 |
| 后期 | Rust HTTP / WebSocket | Rust 拥有会话、调度、历史、进程与存储 | 仅剩明确列出的临时 SDK 桥 |
| 目标 | Rust 后端可执行程序 | MultiCC 自有后端逻辑均由 Rust 实现 | MultiCC 后端不再依赖 Node.js 运行 |

后期仍通过相同 HTTP / WebSocket 协议服务网页和 Flutter。Electron 可以直接启动 Rust 后端并沿用现有就绪检测；是否更换桌面壳是独立决策，不是完成后端迁移的前提。外部 Claude、Codex 等 CLI 仍按它们自己的运行要求安装；“MultiCC 后端脱离 Node.js”不等于“机器上所有第三方 CLI 都不需要 Node.js”。

**接入方式选择**

| 方式 | 适用性 | 本项目建议 |
| --- | --- | --- |
| 独立 Rust 进程，通过有版本的协议调用 | 可独立构建、回退和隔离故障；后续能自然演进为主后端 | 主路线 |
| N-API / napi-rs 原生模块 | 适合频繁调用的计算函数，但共享 Node.js 进程和崩溃影响，增加原生包分发要求 | 只有测量证明进程通信成本成为瓶颈时再考虑 |
| WebAssembly | 适合需要跨端复用的纯算法；文件、进程和网络仍需要宿主能力 | 不作为后端迁移主路线 |
| 直接一次性替换整个服务 | 同时改变大量接口、恢复行为与平台集成，回归面过大 | 不建议 |

第一版 Rust 进程可使用标准输入输出上的逐行 JSON 协议，避免新建公开网络入口。固定 `protocolVersion`、`requestId`、操作名、参数、错误码、超时和取消语义；标准输出只传协议，日志写标准错误。限制单帧大小、队列长度和并发数量，批量传递索引任务，避免逐 token 或逐字符通信。后续需要多客户端接入时，再评估 Unix socket / Windows named pipe 或受认证的本机 HTTP。

推荐的候选技术是 Tokio（异步运行与进程）、Axum/Tower（HTTP、WebSocket 与中间件）、Serde（数据契约）、rusqlite（沿用 SQLite）以及结构化日志工具。它们属于候选，不是本轮已经引入的依赖。SQLite 同步调用应放进明确的数据库工作线程或受限阻塞执行器，避免阻塞异步运行线程；Rust 多线程不取消 SQLite 的写入串行约束。

**按什么顺序迁移**

| 批次 | 移交的职责 | 为什么这样排 | 退出本批的条件 |
| --- | --- | --- | --- |
| 0：建立契约与基线 | 接口清单、事件样例、崩溃恢复场景、资源测量、Rust 构建与通信骨架 | 为后续每批提供同一套对照方法 | 基线可重复，协议能协商版本，受支持平台可构建 |
| 1：消息索引与网页检索 | `src/search/` 对应职责，先接网页搜索 | 数据可重建、实现相对集中，有现成测试 | 查询结果一致、故障可回退、整体资源收益可接受 |
| 2：独立读服务与工具能力 | 经测量选出的日志读取、统计、文件扫描；再逐个迁移无状态业务路由 | 逐步扩大 Rust 覆盖，避免先接管所有状态 | HTTP 兼容、权限一致，旧实现可按域撤下 |
| 3：会话数据与进程宿主 | 历史持久化、CLI 进程监督、流事件标准化；按 CLI / 会话逐批切换 | Rust 开始掌握核心资源，完整承接生命周期 | 新旧格式兼容、取消/断线/重启恢复通过、无重复执行 |
| 4：任务与调度核心 | 任务壳、队列、投递、等待、归类结果应用、Git 操作协调 | 这些模块共享业务不变量，应按完整事务边界移交 | 单一写入者、幂等投递、FIFO 与状态裁决一致 |
| 5：主入口与剩余适配 | Rust 接管启动、HTTP / WebSocket、MCP 工具服务、IM、语音、推送、定时与更新整合 | 完成后端职责闭环，逐项清除 Node.js 桥 | 发布包能以 Rust 独立运行，剩余桥清零，兼容与升级验证通过 |

批次表达风险次序，不要求每个模块严格串行。某些无状态路由可以较早迁移；状态拥有者与调用它的写路径必须一并规划。语言迁移期间尽量保持数据库格式与外部协议稳定，减少同批同时换语言、换库、换业务规则的叠加风险。

终端目前使用 [tmux 与 FIFO](../src/tmux.js)，可由 Rust 继续调用；不要把同时自研终端复用器列为必要工作。Git 层可先继续调用系统 Git，保留 [仓库操作协调器](../src/repo-actor.js)的串行和租约语义，无需为了语言统一立即替换成 Git 库。

**首个试点的具体切法**

首选“消息索引和检索”，理由是可以接触真实后端负载，同时避免一开始就拥有任务投递或聊天历史的写权限。它是候选试点，并非已被性能剖析确认的最大瓶颈。

当前检索并不只供网页使用：[任务归类状态机](../src/classify/state-machine.js)也会读取消息命中作为候选证据，并在回合结束后触发增量同步。因此首轮实施需限定入口，防止检索差异改变任务归属。

1. 从固定、脱敏的 JSONL / 旧 JSON 数组样本生成两套可重建索引；Rust 只读原始历史，写自己的索引文件。Node.js 与 Rust 不共同写同一个索引文件。
2. 先做离线差分，再采样运行影子查询：正式结果仍用 Node.js，Rust 结果只用于比较。对影子查询设置预算，避免双份索引工作压垮主机。
3. 将网页消息搜索入口改为可等待的异步调用，再选择性接入 Rust。当前 `findMessages()` 和调用方是同步接口，不能只替换函数返回值就宣称兼容。
4. 任务归类暂时沿用 Node.js 检索；只有结果、排序、排除当前会话、时效和故障行为验证一致后，才把相关调用链改为异步并切换。
5. 对 Rust 查询不可用进行明确降级；过渡期间允许切回 Node.js 查询。退出试点后删除长期双重索引机制，避免把双份 CPU 和内存消耗变成永久成本。

搜索一致性要覆盖中文二元分词、NFKC 归一化、大小写、单字查询、标点、排序并列规则、过滤条件、增量追加、历史截断、删除会话、半写尾行及索引重建。尤其注意现有高亮范围使用 JavaScript 字符串下标：Rust 的字节偏移或 Unicode 标量下标不能直接当成 UTF-16 偏移返回。

当前全文索引底层已经是原生 SQLite FTS5。改用 Rust 调用同一引擎，并不能自动使索引算法快很多；潜在收益更多来自解析、分词、内存布局与把工作移出主事件循环。应同时比较 Node.js 工作线程或独立 Node.js 进程方案，区分语言收益与进程隔离收益。

**如何验收性能与正确性**

本轮没有 Rust 基准数字。代码注释中的历史测量不作为本轮复测结论。建议下一轮用同一机器、同一固定语料、同一算法与 SQLite 配置，分别比较现有 Node.js、隔离执行的 Node.js、Rust；Rust 使用优化构建，并分别报告冷启动与热态结果。

| 验收项 | 必须得到的证据 |
| --- | --- |
| 语义一致 | 固定样例与随机样例的结果、顺序、高亮、错误语义逐项对照；浮点得分若采用容差，须预先定义，且不能掩盖顺序变化 |
| 用户体验 | 搜索请求 p50/p95/p99、并行聊天时主服务事件循环延迟、首个结果可用时间 |
| 总成本 | Node.js 与 Rust 进程合计 CPU、合计常驻内存、峰值内存、磁盘读写与索引体积，包含 IPC 和重复缓存 |
| 增量行为 | 全量建立与小批追加分别测量，不能拿全量重建的加速代表每次请求都加速 |
| 故障隔离 | Rust 崩溃、超时、协议不兼容、磁盘写满时，聊天继续可用，降级结果可识别 |
| 部署 | macOS、Linux、Windows 所支持架构的安装、启动、退出、升级、回滚验证 |

试点成功的建议判据：正确性用例全部通过，并且至少一个真实目标指标显著改善，例如并发聊天时的尾延迟或总 CPU；其他关键指标不出现不可接受的回退。具体阈值应在采集基线后、查看 Rust 结果前确定。若隔离后的 Node.js 已满足需求，Rust 试点仍可用于验证长期迁移基础，但应如实记录性能收益有限。

大模型等待、供应商网络延迟、外部 CLI 内部执行不会因 MultiCC 换语言直接缩短。例如，本地后端只占某次请求总耗时的 10%，即使这部分快 10 倍，总体也仅约快 1.10 倍；这里是比例说明，不是本项目测量。

**核心迁移中不能遗漏的行为**

- 状态与副作用：保留消息幂等键、队列顺序、归类裁决、已持久化证明、重试与恢复关系。不要同时运行两套会真实执行 CLI、发送通知或合并 Git 的影子写路径。
- 写入者切换：先停止该业务域接受新写入，排空旧写入与活动工作，完成持久化检查，再以所有权代际或等价机制交接。对于“事务可能已提交但响应丢失”，先按幂等键查证，不能盲目转交旧实现重做。
- 存储兼容：保留旧 JSON 数组与 JSONL 的读取语义、损坏识别、SQLite 事务和升级回退路径。Rust 类型反序列化要区分字段缺失、`null`、空值、整数边界与未知字段。
- 进程生命周期：明确谁拥有 CLI 子进程、怎样回收、怎样处理退出但未清理的进程、取消升级信号、常驻会话与后台任务。Tokio 不会自动把任意进程树管理变正确；其官方文档明确说明丢弃子进程句柄默认不会结束子进程。
- 流协议：保留事件顺序、重连补发、去重、慢客户端背压、缓冲上限和错误结束行为；HTTP 返回兼容不能代替 WebSocket 行为兼容。
- 权限与隐私：沿用现有鉴权、本机请求判断、WebSocket 票据、目录隔离、下载路径校验、密钥注入与日志脱敏。若通过本机 HTTP 转发，不能让外部请求因“代理来源是本机”获得本机免鉴权待遇。
- 发布与平台：当前[发布工作流](../.github/workflows/desktop-release.yml)含多平台多架构；要补 Rust 二进制签名、校验、运行依赖和旧系统版本兼容，保持用户安装时无需本地 Rust 编译器。

目前用户的“运行中服务只能手动重启”约束也应在实施中保留。迁移方案应支持按域逐批交接；本次调研没有重启服务。

**Node.js 最难退出的部分**

| 现有依赖或能力 | 迁移期处理 | 最终退出要求 |
| --- | --- | --- |
| `@anthropic-ai/claude-agent-sdk` 与常驻流宿主 | 暂保留受限 Node.js 桥，先稳定外部协议 | 核实官方可用的 Rust / 协议能力或实现等价进程协议；逐项证明恢复、取消、工具与事件一致，不能假定已有同等 Rust SDK |
| `cli-provider-router` 与供应商策略 | 暂保留代理桥，Rust 调用已有协议 | 将路由、流转发、协议转换、配额与账号隔离逐项移交；保留供应商差异测试 |
| 飞书、Slack、Discord、Telegram 等 SDK | 按渠道维持小桥，避免阻塞核心迁移 | 基于官方协议或核验过的 Rust 库替换；覆盖重连、事件确认、重复事件、媒体上传 |
| `sherpa-onnx-node`、`werift` 等语音与实时能力 | 暂保留边界清楚的工作进程 | 另行核实原生接口与 Rust 生态的功能、平台和打包兼容；不能只替换包名 |
| MCP 工具、安装更新与服务管理 | Rust 主后端上线前可继续沿用既有组件 | 工具名、参数、错误、传输和服务生命周期兼容，并完成运行依赖盘点 |

因此“Rust 主后端已经上线”与“Node.js 完全退出”应分成两个验收里程碑。桥是有清单、负责人和退出条件的临时组件；目标若要求所有 MultiCC 后端功能都用 Rust，实现这些尾部能力必须计入总范围。

**投入和停止条件**

以有 Rust 与 Node.js 经验、熟悉现有业务的工程师估算：第一个隔离试点可先安排 2～4 人周预算，包含接口整理、原型、差分与测量；这是探索预算，不是上线承诺。一个试点完成后再据实际速度估算下一批。

完整后端约 13.9 万行主体代码，另有大量协议、测试与平台集成；如果由 2 名有经验的后端工程师持续投入、配合测试和发布支持，且功能范围相对稳定，可先按 6～12 个月量级做立项预算讨论。该区间是低置信度工程判断，不是由行数换算的工期；供应商 SDK 等价性、持续新增功能、跨平台尾部适配都可能显著拉长周期。
