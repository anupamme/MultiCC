客户端直连，还是服务端中转？

两种做法的根本区别在两件事：谁去连谁，以及另一台电脑的凭证放在哪。

服务端中转：  手机/浏览器 ──▶ 电脑 A ──▶ 电脑 B        凭证在 A 的服务端；只要求 A 能连到 B
客户端直连：  手机/浏览器 ──▶ 电脑 B（直接）           凭证在客户端；要求客户端此刻能连到 B

0. 结论

直连在 App 上是最自然的做法，在浏览器上是最难的做法。
· App：没有跨域、混合内容、浏览器权限这些限制；而且 App 的「单服务器」假设集中在一个对象上，改造面可控。推荐 App 直连，并作为主力客户端。
· 浏览器：同页无刷新直连会同时撞上四道墙（下文第 2 节）。可行的直连方式是「切换 = 跳到那台电脑自己的 Air 页面」，用一次性登录票据免去重复登录。体验是「切换时刷新一次页面」，不算完全无感，但不需要中转。
· 唯一必须接受的代价：客户端此刻必须能连到那台电脑。手机在外网时，每台电脑都得有自己的外网地址（隧道）；只在内网的电脑，在外面就看不到。

1. App（Flutter）直连：调研结果

平台限制对 App 不成立。App 用的是 Dart 自己的网络栈，不受浏览器的跨域、混合内容、Local Network Access 限制； App 现在已经能连 http://192.168.x.x（局域网发现填的就是这种地址，Info.plist 已声明 _multicc._tcp 和本地网络权限）。
项现状（代码证据）直连要做的
单服务器假设42 个文件、211 处请求都通过 SettingsService.buildHttpUrl 拼地址，令牌也从同一个对象取；共 90 个文件依赖它它就是唯一的切换点：引入「当前电脑」上下文，切换时整体换掉 host + token，通知各服务重载。不需要改 211 处调用。
多服务器凭证settings_service.dart 已有「服务器历史」（地址 + 令牌，按 host 去重）升级为「电脑列表」：名称、颜色、多个候选地址（内网 / 外网）、令牌
实时连接WsTicketClient 每次连接都向当前 host 换一张一次性票据不用改：直连时 host 本来就是那台电脑的根地址（中转方案反而要改这里）
推送切换服务器时会从旧服务器注销推送（fcm_service.dart:168-174）改成向所有已加入的电脑同时注册推送，并在通知里带上电脑 id，点开时自动切到那台。这是「无感」最关键的一处。
其它电脑的状态无App 在前台时每 15–30 秒直接拉各台电脑的轻量摘要；后台靠推送
内网 / 外网地址connection_probe_service.dart 已能探测地址每台电脑存多个候选地址，按「内网优先、外网兜底」探测，记住最近一次能通的那个

体验：点切换器 → 约 0.5 秒换完（与现在换服务器一样会重新拉数据，但不用重新登录、不丢推送）。任何电脑上的「等你回复」都会推送到手机，点开就落在那台电脑的那个任务上。

2. 浏览器直连：四道墙

「同一个 Air 页面里无刷新切到另一台电脑」，要求浏览器从 A 的页面直接请求 B 的接口：

墙现状 / 事实能不能翻
① 跨域（CORS）服务端完全没有 CORS 头（全仓搜不到 Access-Control-Allow）；前端 api-client.js 默认拒绝跨域请求能，但要给每台电脑的所有接口加 CORS，并精确限定允许的来源
② 登录态登录 Cookie 是 SameSite=Lax、按域名隔离（auth.js:71），A 页面带不上 B 的 Cookie；第三方 Cookie 正在被浏览器淘汰只能把每台电脑的令牌存在 A 页面的本地存储里，用请求头发出去。任何一台电脑的页面出现 XSS，所有电脑的令牌一起泄露
③ 混合内容A 页面经隧道是 https，B 在内网是 httpChrome 对「写明内网 IP」的 http 请求有豁免，但要用户授权（见 ④）；Safari（含 iPhone 上所有浏览器）没有这个豁免，直接拦截
④ 本地网络访问权限Chrome 142（2025-10）起，公网页面访问内网地址会弹「查找并连接到本地网络上的任何设备」的授权框；据第三方资料，WebSocket 从 Chrome 147 起也受限；iframe 里的页面还要父页面委派权限能，但每个浏览器首次都要授权；对话页是 iframe，需要额外委派
四道墙都翻过去之后，还剩版本差异：前端是 A 的、接口是 B 的，两台版本不同就可能出错（中转方案也有这个问题）。所以浏览器的「同页无刷新直连」投入大、坑多、还不稳，不建议做。

浏览器的可行直连：跳到那台电脑自己的页面

你在 A 的 Air 里点「切到 Mac mini」
  → 浏览器跳到  https://mini 的地址/air?login_ticket=一次性票据
  → Mac mini 验票、种下自己的 Cookie、抹掉地址栏里的票据（复用现有 ?token= 引导兑换流程）
  → 你看到的是 Mac mini 自己的 Air：自己的前端、自己的接口，没有跨域、没有版本差异
  • 一次性登录票据从哪来：客户端（App 或浏览器）配对时拿到每台电脑的令牌，用它向那台电脑换一张 60 秒、只能用一次的登录票据。浏览器里不长期保存令牌，只在切换的那一刻用。
  • 切换器和「其它电脑」状态条：每台电脑的 Air 都要显示别的电脑的状态，需要一个只读、只返回计数的摘要接口开放跨域。只开这一个接口，风险可控。
  • 电脑列表怎么同步：列表本身（名称、颜色、地址，不含令牌）保存在每台电脑上并互相同步，这样无论从哪台电脑打开，看到的列表都一样。
  • 限制：浏览器此刻必须能打开 B 的地址。手机浏览器在外网时，B 必须有外网地址。整页跳转不受混合内容限制（跳过去整页都是 B 的），这道墙只拦跨域请求。

3. 横向对比

你打开的那台电脑关机全都切不过去互不影响互不影响
延迟 / 带宽多一跳；远程屏幕走两段网络最短路径最短路径
另一台电脑的凭证在哪服务端文件（0600）App 本地浏览器只在切换时短暂使用
切换体验Web 整页刷新约 1 秒约 0.5 秒，最接近无感跳页面，约 1–2 秒
推送A 汇总后再推每台电脑直接推给手机同现在（各自 Web Push）

以后做方案 B（统一控制台）A 汇总，前端改动大App 同时连 N 台、本地聚合，顺理成章很难（又回到四道墙）

4. 推荐：客户端直连为主

服务端（各台都一样，约 3 天）

  • 配对：B 显示配对码 → 客户端用码向 B 换一枚设备令牌（可单独吊销，不用暴露 ACCESS_TOKEN）
  • GET /api/machine/summary：只读计数，开放跨域
  • POST /api/auth/login-ticket：设备令牌换 60 秒一次性登录票据
  • 电脑列表（不含令牌）在各台之间同步

App（主力，约 4–5 天）

  • SettingsService 加「当前电脑」上下文，一处切换
  • 服务器历史升级为电脑列表 + 多候选地址探测
  • 推送向所有电脑注册，通知点开自动切机
  • 侧栏顶部切换器 + 其它电脑状态

Web（约 3 天）

  • 侧栏切换器、页顶色条、「其它电脑」状态条（读各台摘要）
  • 切换 = 拿登录票据，跳到那台电脑的 Air，带上当前视图
  • 连不上的电脑如实显示「当前网络访问不到」，并给出它的地址供排查

总计约 10–11 天，和中转方案相当，但工作量从服务端移到了 App。服务端中转可以先不做；以后真遇到「外网手机要看只在内网的电脑」，再把它作为兜底加回来，两者不冲突。

5. 需要你确认的

  1. 浏览器里切换电脑时跳页面（刷新一次）可以接受吗？浏览器要做到同页无感，只能靠中转，或者硬翻上面的四道墙。
  2. 手机在外面时，想用的每台电脑都有自己的外网地址吗？如果有电脑只在内网，纯直连在外面就看不到它，要么接受，要么保留中转作兜底。
  3. 主力客户端是 App 还是浏览器？如果是 App，就先做 App + 服务端，Web 跟上。
