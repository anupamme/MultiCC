打开 MultiCC，先看到要做的事

推荐把多台电脑上的待办、最近任务汇到一个入口；电脑保留为明确的执行位置。连接方式服务于这个体验，不能反过来决定整个产品。

本次不沿用 A / B / C 的既定选择。假设主要用户是拥有数台电脑、会在手机与电脑之间继续工作的个人用户；此假设尚未通过用户访谈验证。研究没有部署竞品，也没有实现 MultiCC 多机连接。

1. 从第一性原理拆开问题

一项工作至少包含：人的意图、任务记录、执行环境、人与执行环境的连接。任务记录应该容易找到；执行环境拥有实际文件、登录态、工具和硬件，不能因为界面统一就假装它们也统一了。

应该消除的负担

记住任务在哪台电脑、反复填地址和登录、逐台寻找待办、网络切换后手工重连、从通知进入后再次寻找对应对话。

应该保留的信息

动作在哪台电脑、哪个目录执行；信息是否最新；命令是否被目标机接收。执行位置和执行结果影响正确性，不能为了“无感”而隐藏。

用户此刻想做的事合适的默认体验可验证的成功标准
手机上看看有没有事情等我跨电脑的“需要我”，按紧急程度与时间排列不用进入任何电脑页，就能发现全部已连接电脑的待办；未连接的范围明确标注
继续刚才那个任务最近任务、搜索、通知都直达原任务不先选择电脑；回来后保留草稿、位置和上下文
给一个项目开新任务选择项目的具体工作目录，自动带出执行电脑已有默认位置时不用再选机器；多个位置时明确选择一次
从家里 Wi-Fi 切到外网同一电脑身份下自动恢复可用连接任务归属不变、无重复发送；无法连接时给出可行动的原因
电脑休眠或失联保留最后已知任务，显示更新时间和连接状态不把失联误报为任务失败、成功或电脑关机
处理某台机器的环境问题电脑页提供版本、连接、资源和本机设置高级管理可达，但不挤占日常任务首页

推导：首页应围绕注意力和工作连续性组织；电脑筛选器仍有价值，但不应成为所有操作必经的第一步。若真实用户几乎只在一台电脑工作、很少跨机处理待办，简洁切换器可能更合适，需要用场景测试验证。

2. 同类产品真正能证明什么

以下来自此次重新读取的官方文档与仓库。它们证明产品提供的能力或公开架构，不代表本次已验证实际稳定性或用户满意度。

产品已核对的做法对 MultiCC 的启发与边界
Happier [1]跨机器会话；新建会话选电脑、目录和 agent；统一 Inbox；机器运行 daemon；relay 同步加密内容，仍可见部分路由元数据。最接近本题：用会话和注意力组织多机体验。它证明这种体验可与 relay 共存，不能用来证明“直连更好”或其全部功能值得照搬。
Happy [2]仓库包含移动/Web 客户端与加密同步 relay，提供跨设备继续会话的能力。手机离开桌面后继续原有工作，是产品价值本身。其 README 中部分新能力属于其他关联仓库，本报告不把它们算作此仓库已实现能力。
VS Code Remote Tunnels [3]客户端选择远程机器；远端执行；登录同一账号；两端向 Azure 服务发起出站连接；编辑器保留远端标识。能隐藏连接配置，同时明确执行环境。它偏重一次深入一处环境，不能替代多任务注意力聚合。
Portainer [4]一个 Server 管理多个 environment。Agent 需要从 Server 可达；Edge Agent 通过轮询、按需隧道适应远端不可直达的网络。同一管理体验可以支持不同连接路径。集中运维适合它，但 MultiCC 不必随之采用一个主控电脑管理所有本地工作。
Home Assistant Companion [5]App 可添加多个 server；局域网发现；内外网地址与 Cloud 连接有独立配置。直接管理多服务器是可行的；地址、证书、网络和远程访问的配置成本不会因为“客户端直连”自动消失。
Omnara [6]machine daemon 出站连接 control plane；agent 的事件记录在 control plane，机器只是可绑定的执行环境。更彻底地分开任务与机器，但这是另一种任务运行模型。不能据此承诺现有 CLI、浏览器登录态和本地文件能无缝迁移。

共同启发：统一入口、稳定身份、远端常驻连接组件、明确的执行环境，是反复出现的组成部分。是否中心化、是否迁移，是另外的产品决策。

未采用：本轮 Cockpit 页面未取得可用正文、另一个官方文章地址返回 404；Tailscale 页面请求未能完成重定向。没有把这些抓取失败当作架构证据。

3. 推荐体验：统一工作入口，局部环境清楚

手机优先展示“需要我 / 最近任务”，电脑宽屏可以同时展示目录。电脑页负责连接与环境管理。选择一台电脑是筛选视图；进入任务是访问该任务固定的执行位置，两者不互相改变。

我的工作

新建任务 · 执行位置

五个关键交互

  1. 添加电脑：在目标电脑打开“连接设备”，用一次性二维码或短码授权客户端。已使用统一连接服务时可关联到同一身份；纯直连模式仍需可达地址。扫码负责建立信任，不负责穿透网络。
  2. 从通知继续：通知携带电脑和任务身份，点击直接进入相应任务；任意客户端处理后，其他端同步消除待办。
  3. 新建任务：从目录发起时沿用该目录；从全局入口发起时选择具体工作位置。可以记住用户选过的位置，不按“哪台机器空闲”擅自换环境。
  4. 同名项目：允许用户把多个工作位置归入同一项目，但保留不同目录、分支、未提交改动与登录态。名字相同、仓库地址相同都不足以证明环境等价。
  5. 失联：展示“连接中断，最后更新于……”，允许查看已有缓存和保存草稿。未得到接收回执的写操作显示“发送结果待确认”；恢复后先查 operationId，不能盲目重发。离线不自动迁移、不自动执行过期操作。

无感的目标是：无需手工处理连接，也无需记住任务在哪台电脑。需要用户判断执行位置时，应清楚展示“工作电脑 · ~/work/site”，尤其是终端、文件修改、任务启动和设备重启。

4. 先判断网络事实，再选连接实现

客户端 C 想操作电脑 B，必须存在一条可用路径：C 能直接访问 B；或借助双方可达的连接服务；或依赖 VPN / 覆盖网络建立可达性。如果 B 既无可达入口、也不建立出站连接，单靠一个前端界面不能让外网手机找到它。

浏览器直连并非技术上不可行：当每台机器都有可达且可信的 HTTPS 入口，并正确实现受信来源 CORS 与独立客户端授权时，同页聚合可以成立。问题在于把这些前提交给多少用户配置，以及本地网络访问的浏览器差异。[7–9]

路径用户得到什么必须付出的代价建议定位
客户端分别直连每台电脑不依赖某台中转电脑；局域网通常路径较短每台需可达；原生 App 仍受系统网络权限与 TLS 配置约束；浏览器要解决 HTTPS、CORS、授权、局域网访问权限App / 原生网络适配器的优先可用路径；自托管直连模式
切换时跳到目标电脑自己的网页沿用目标电脑现有页面，避开同页跨域请求页面与本地存储按 origin 分开；聚合状态、返回位置、登录接力还要另外做；原入口不可达时有入口恢复问题快捷打开、诊断与渐进兼容；不作为“完全无感”的最终体验
当前电脑 A 代理 B、C浏览器只面对一个 origin；容易接入现有 HTTP 接口A 休眠或断网可能同时遮住 B、C；A 持有跨机访问权；大流量绕路只有用户明确把 A 当常开网关时才合理，不默认强加给日常工作电脑
独立连接服务；各电脑出站连接固定 Web 入口；无需逐台开放入站端口；客户端不必理解内网地址常在线服务、维护和流量成本；服务失效会影响经它访问的机器；身份、授权、数据可见范围必须设计若目标是普通用户跨网络打开就能用，这是推荐的完整体验基础；允许自托管
VPN / 覆盖网络可以复用现有可达性，减少端口暴露客户端安装与组网成本；不会自动解决网页的同源、HTTPS 与任务身份问题已有组网用户的可选接入方式，不要求所有用户安装

明确推荐：统一的客户端工作模型，可替换的连接层

Web / App：任务、待办、电脑身份→授权后的直连
或独立连接服务→每台电脑上的 MultiCC
本地任务 / 文件 / 工具

面向完整的跨网络体验：Web 默认经稳定的独立连接服务访问电脑，电脑主动建立出站通道；原生 App 可在确认目标身份与路径可用后直连，并在已配置的连接服务上兜底。各电脑平等执行任务，连接服务不成为任务调度者，不要求另一台日常电脑一直开机。

面向拒绝常驻连接服务的用户：保留纯直连模式。已拥有可信 HTTPS 入口的用户可以获得同页 Web 体验；否则 App 直连更自然，Web 可以先提供快捷打开各机器。必须明确外网可达性由用户环境提供，不能把“免服务、免配置、任意网络可达”同时许诺。

这不是要求第一版同时实现所有路径。先验证统一体验；若“浏览器跨网络无配置”是发布目标，就优先验证出站连接服务；若首批用户已有外网地址且主要用 App，则先交付直连。路径选择不放到日常任务页面。

边界条件不能隐藏

  • 电脑失联与连接服务失联分别呈现；服务不可用时，已授权且可直达的客户端仍可工作，远程路径不可达的就明确不可用。不能承诺所有故障自动绕过。
  • 直连优先不等于先等很久才尝试其他路径。需要有限超时、路径健康缓存、防抖；路径切换始终校验同一 machineId 与授权身份。
  • Web 后台与手机后台都不能靠永久保持前台 socket 保证通知。多机通知注册、去重、点击定位与撤销必须单独设计。
  • 连接凭证和模型 API key 是不同东西。每个客户端用可撤销的连接授权；模型密钥、浏览器登录态和本地文件默认留在执行电脑。
  • 经第三方 relay 时应优先设计端到端的应用消息加密，并明确元数据可见范围；普通 TLS 反向代理会在网关解密，不得称作端到端加密。本建议尚未完成该协议实现与安全验证。
  • 终端、文件下载、上传、语音、远程屏幕都必须纳入路径验证。只跑通聊天 JSON 不能宣布整个 MultiCC 已多机无感。

代码证据含义推荐改法
app/lib/services/settings_service.dart:99, 234, 361, 488：单一 host、session；部分缓存按 sessionId 保存；URL 从当前 host 构造。换一个全局地址容易；同时维护多机任务、旧请求响应和缓存归属是另一件事。引入按 machineId 管理的连接对象；任务、缓存、草稿用 machineId + task/sessionId 命名空间。请求和回调绑定发起时的目标，不读取可变全局 host。
app/lib/services/fcm_service.dart:168–180：binding 变化会删除旧 host 的推送注册。切到另一台电脑可能影响旧电脑通知。按电脑独立保留注册、续期与撤销；通知携带完整任务地址，多端处理后去重。
public/api-client.js:182–236：跨域要 opt-in；跨域敏感 header 被移除，credentials 为 omit。src/routes/auth.js:71 使用 HttpOnly、SameSite=Lax cookie。当前浏览器客户端不支持直接把已登录凭证拿去请求另一台电脑。添加明确受信的多机传输接口与授权协议，不能简单全局放开跨域或复用万能 token。
app/lib/services/ws_ticket_service.dart:62–99 要求 host 是 origin；src/routes/fleet-sharing.js:219–265 已有 scoped HTTP 转发与远端 WS 换票。可以借鉴票据和授权边界；不能认定给 URL 加路径前缀就能转发全部能力。能力清单、独立传输契约、流式通信和文件访问逐项验证。跨机摘要不拉取全量聊天历史。
src/lan-discovery.js:9, 24–32, 45–55 已有带条件的 mDNS 服务广播。局域网发现可以复用，但发现地址不代表完成授权，也不提供互联网发现。将发现、稳定机器身份、信任配对和连接健康分开。

6. 实施顺序与验收门槛

第一版目标建议定为：两台电脑上的待办集中可见，点击直达对应任务；打开、回复与断线恢复不会混淆电脑。这比先完成一整页运维面板更直接地验证用户价值。

  1. 验证体验：用本页示意让 3–5 位多电脑用户完成“找待办、继续任务、选工作位置、解释失联”四件事。记录是否先找机器、是否误解执行位置。此项尚未执行，不能把推导当作用户验证。
  2. 验证连接契约：先实现稳定 machineId、客户端授权、最小摘要与能力/版本协商。用两台真机、两个同名目录测试隔离；验证 HTTPS 入口与仅私网入口、局域网转蜂窝网络、休眠和授权撤销。Web 至少覆盖 Chrome 与 Safari，App 覆盖 iOS / Android。
  3. 交付最小闭环：跨机“需要我 / 最近任务” → 正确任务 → 回复 → 原机确认 → 其他端待办消除。离线仍保留最后更新时间。读取摘要可增量、分页、有限并发；只给当前任务建立重流量连接，坏机器不拖住首页。
  4. 补齐使用连续性：多机推送、深链接、草稿、重连回执、文件与终端路径。再按实测决定直连优化和远程屏幕等重流量能力。
  5. 最后扩展：明确项目与多个工作位置的关系，按需求补电脑管理。跨机自动调度、任务迁移、批量升级、密钥同步都不是本轮体验成立的前提。
必须通过的测试场景通过条件
家用电脑正在显示时，工作电脑任务请求输入全局待办可见；点击进入工作电脑的正确任务，回复不落到家用电脑
快速切任务，旧请求晚返回旧结果只能更新原机器对应缓存，不能覆盖当前视图或授权
发送后立刻断网，目标可能已接收有操作 ID 与接收状态；重连查证，不重复启动任务、不虚报成功
同名目录、克隆数据产生相同本地任务 ID电脑命名空间仍能隔离任务；更换 URL 不生成第二个机器身份
电脑休眠 / 连接服务不可用 / 会话权限被撤销区分可证实的状态与未知原因；其他可达电脑继续使用；撤销生效
从通知打开；在另一端先处理定位不依赖“当前电脑”，已处理请求不重复出现

可以给首次摘要与切换时延设性能预算，但当前没有实测基础，不用虚构毫秒数字作结论。还需要补测不受信证书、各端局域网权限、代理子路径、旧版本节点和大文件传输。

7. 什么证据会改变这个推荐

  • 如果用户长期只用一台、偶尔开另一台：缩减为切换器加跨机待办提示，不强制全局首页。
  • 如果主要用户已有 VPN / 可信外网入口、且以 App 为主：先做客户端直连，连接服务后置。
  • 如果“任何浏览器打开一个网址就能用”优先级最高：独立连接服务与出站连接是前置工作；不能用跳页原型冒充最终体验。
  • 如果用户主要诉求是把无状态任务投给空闲机器：需要另行研究资源调度、环境声明和失败恢复；当前推荐不能替代调度系统。

本次结论：最值得先做的是工作层面的统一，而不是把电脑管理做得更复杂。界面采用统一待办、最近任务和明确执行位置；连接实现采用独立接口，保留直连能力。完整跨网络体验应有稳定连接服务承担可达性，不能默认依赖任一工作电脑充当中转站。

  1. Happier：README：“pick the machine, the folder and the agent”；Inbox：“What needs my attention right now?”；Daemon。README 说明 relay 可见 session ids、timestamps、turn status 和 usage metadata。
  2. Happy：README：“the relay server for encrypted sync”。
  3. VS Code：Remote Tunnels：“both cases, VS Code will make outbound connections to a service hosted in Azure”；也说明远端必须保持服务运行。
  4. Portainer：Environments、Agent、Edge Agent：“without having to open any ports on the environment”。这不代表 Server 也不需要可达端口。
  5. Home Assistant Companion：Getting started / Adding additional servers、Networking。用于确认多服务器与内外网配置能力，不照搬其中所有网络部署建议。
  6. Omnara：Machines overview：“the machine does not own the agent”；“connects outbound to the control plane”。
  7. MDN：CORS。服务端可以授权跨域；跨域不是浏览器直连绝对不可行的证明。
  8. MDN：Mixed content。HTTPS 页面访问 HTTP 资源受到限制；需要按具体平台与资源类型验证。
  9. Chrome：Local Network Access。官方说明 Chrome 142 引入权限提示；不能推断所有浏览器具有相同行为或例外。
