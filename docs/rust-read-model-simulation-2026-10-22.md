# Rust 任务读模型模拟评测 · 2026-10-22

结论：有针对性的 Rust 后台读取值得进入下一轮验证，但不建议整体切换。最有价值的边界是“Rust 直接读取 SQLite 的原始记录 → 提取卡片摘要 → 持有读模型”，避免大段上下文变成 JS 对象再搬回 Rust。普通缓存命中、日常写入和小规模卡片更新暂时保留 Node 更合适。所有实验均在隔离进程和临时数据库中完成，生产路由、数据库、原生模块入口和配置未修改。

## 测试范围与公平基线

环境：Apple M4，darwin/arm64，Darwin 24.3.0，Node v26.8.1，rustc 1.98.0 (88d9e12ae 2026-08-18) (Homebrew)。源码基线 79caa761f9e712ac2865ecbf2c09fd66fc93ed93。测试时间 2026-10-21T17:27:42.481Z（UTC）。未在 2013 Intel MacBook 上测试。

四种实现：直接使用现有 createAirReadIndex；独立的增量 Node 原型；相同增量 Node 在工作线程中运行；通过 napi-rs AsyncTask 调用的 Rust 原型。两种增量实现均采用映射表、有序数组、增减计数和有界分页缓存，大批变更才重新排序。Rust 已使用固定字段结构，并跳过摘要不需要的正文解析；它不是通用 JSON 对象版本的初稿。

数据规模为 100、1277、3000、10000 条。每条任务包含 8192 字符上下文、4 条引用，分布在 10 个目录，包含运行、等待、出错、完成、归档、待办、忽略和置顶等状态。数据全部为合成数据。

每场景预热 2 次、测量 15 次，表中是中位数，单位为毫秒。每种后端与数据规模使用独立进程，依次运行，不同规模轮换后端顺序。原始文件保留 P95、最大值、CPU 时间和主线程心跳。系统文件缓存预热，不是物理磁盘冷启动；本机其他程序可能影响尾部延迟，15 个样本不足以作为生产 P95 服务指标。

Node 使用 SQLite 3.53.4，Rust 使用 SQLite 3.50.2。SQL、表结构、数据和 WAL/NORMAL 设置相同，但 SQLite 版本不同，数据库倍数不能全部归因于编程语言。

计时包含主线程参数编码、跨线程/原生边界、排队、后台计算及结果解码。摘要构建还包含 Node 将源记录投影为卡片的时间。Node 直接调用无需额外跨语言拷贝；工作线程与 Rust 使用相同 JSON 请求边界。SQL 写入使用同一事务和同样的完整记录，未模拟完整业务层的权属、收据和二级索引联动。

## 为什么不能把整份任务对象反复传给 Rust

| 任务数 | 源数据 MiB | 摘要 MiB | 现有 Node 构建 | Rust 接收完整源记录 | Rust 接收摘要 |
| --- | --- | --- | --- | --- | --- |
| 1277 | 10.66 | 0.44 | 4.63 | 34.38 | 4.67 |
| 3000 | 25.04 | 1.04 | 11.73 | 84.61 | 10.74 |
| 10000 | 83.50 | 3.46 | 39.70 | 333.04 | 45.20 |

Rust 后台执行不代表整个请求不阻塞主线程。完整记录先在 Node 里 JSON.stringify，这部分仍在主线程；把大量不需要的上下文搬过去会抵消后台计算的收益。生产设计必须传增量或直接由后台读取存储。

## 数据库：先排除临时排序，再看 Rust 直接读取的收益

现有 shell_records 的主键为 (kind,id)，查询使用 WHERE kind='task' ORDER BY rowid。EXPLAIN QUERY PLAN 显示 USE TEMP B-TREE FOR ORDER BY。模拟库增加 CREATE INDEX experiment_kind_rowid ON shell_records(kind) 后，SQLite 可利用索引中隐含的 rowid 顺序，临时排序消失。该索引没有加入正式数据库。

| 同样附加索引 | 最快已测 Node 路径 / ms | Rust 直接读取并构建 / ms | 加速比 |
| --- | --- | --- | --- |
| 1277 条任务 | 18.11 | 4.74 | 3.82 倍 |
| 3000 条任务 | 44.23 | 13.32 | 3.32 倍 |
| 10000 条任务 | 158.78 | 43.32 | 3.67 倍 |

上表按规模选择本次最快的 Node 路径（包含工作线程，可能选择不同方案），两侧输出相同摘要读模型；不是拿全表 Node 与已经加索引的 Rust 混比。下面保留所有分项，便于核对。

这不是单纯把 SQLite 从 Node 换成 Rust 的收益：Rust 在后台用固定结构选择性解析 JSON，大段上下文不会被构造成 V8 对象，摘要也留在 Rust 内。SQL 层逐字段提取并非总是最优；Rust 在此数据集上直接读取原始 JSON、忽略无关字段，比让 SQLite 逐字段生成摘要更快。所有倍数仅代表这几种已测实现，不能当成 Rust 对任何 Node 实现的通用倍数。

## 主线程响应性与内存

| 3000 条任务场景：最大心跳间隔的中位数 | 现有 Node | 增量 Node | Node 工作线程 | Rust 异步 |
| --- | --- | --- | --- | --- |
| 摘要构建 | 9.87 | 8.06 | 4.50 | 5.58 |
| 原结构全记录数据库读取 | 248.09 | 254.05 | 1.68 | 1.33 |
| 附加索引全记录数据库读取 | 61.76 | 59.32 | 2.14 | 1.32 |

心跳使用 1ms 定时器，约 1～2ms 是本机定时器及调度噪声。后台数据库读不会让主线程同步等待整个 SQL 操作；Node 工作线程也能提供这一优势。主线程编码大请求仍可能造成长停顿。此探针不是 HTTP、WebSocket 或页面渲染的端到端测试。

| 完整模拟过程峰值 RSS / MiB | 现有 Node | 增量 Node | Node 工作线程 | Rust 异步 |
| --- | --- | --- | --- | --- |
| 3000 条任务 | 360.8 | 381.5 | 775.6 | 335.3 |
| 10000 条任务 | 749.6 | 682.3 | 2046.2 | 787.0 |

RSS 为整个独立进程，包含合成数据、Node、SQLite、Rust或工作线程，以及多轮测试产生的临时分配；不能当作某一个库的精确内存占用。工作线程还包含额外的 V8 堆。Rust 在所有规模上并未稳定小于增量 Node，不能据此承诺省内存。

## 正确性与尚未覆盖的生产契约

已通过 318 组逐字段对照，每组比较四种后端，覆盖重复快照、原地变更、跨目录变化、删除、空列表、所有模拟筛选、中文与 emoji 标题、置顶、访问排序、指定 ID 排序、同时间排序以及统计。数据库原结构和附加索引结构均通过全记录/摘要等价、批量写入、失败回滚、重新打开、完整上下文未丢失检查，共 3 个测试用例。Rust 格式检查和 Clippy 严格检查通过，JavaScript 语法检查通过。

这是有限合同的模拟，不是可直接替换的生产实现。尚未实现或完整验证权限判断、Git 状态、动态容量、派发时间宽限、跨连接变更通知、WebSocket 游标与重放、并发命令顺序、崩溃恢复、升级回滚及所有异常输入。输入 ID 使用固定 ASCII 格式、时间使用有效整数；不能据此推断任意 locale 排序和 JavaScript 隐式转换完全等价。

仓库行数检查仍报既存问题：server.js 为 3020 行，上限 3000；该文件与本轮基线一致，未修改。实验代码未加入生产 native workspace，也没有更改生产路由、构建工作流或启动开关。

## 切换建议

保持生产逻辑不变。若用户决定继续，建议只把“数据库重型读取＋摘要读模型”作为 Rust 的下一步试点，同时保留查询索引优化；先做真实数据的只读对照和故障测试，再决定启用。日常卡片更新可以先采用增量 Node；普通数据库写入和分页缓存命中不值得单独跨语言调用。Node 工作线程能改善响应性，但本次重型读取耗时和整体峰值内存不及 Rust。

正式切换前，应以真实请求分布、完整接口一致性和用户可感知的毫秒收益作为门槛。不能依据某个单卡更新的十几倍比值整体迁移，也不应把本次 SQL 索引改进算作语言改写收益。
